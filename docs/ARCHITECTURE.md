# Архитектура ym-discord-rpc

Коротко: демон читает плеер Яндекс Музыки через MPRIS, находит трек в каталоге (обложка, id, ссылки), собирает Discord activity и отправляет её в локальный клиент Discord через IPC-сокет. Приложение Яндекс Музыки он не меняет и ничем в нём не управляет.

## Модули

```
src/
  main.ts                 точка входа: конфиг, сигналы, DiscordIpc или ConsoleSink (dry run)
  app.ts                  связка: источник → engine, плюс один поиск в каталоге на каждый трек
  config.ts               чтение ~/.config/ym-discord-rpc/config.json поверх DEFAULT_CONFIG, env-переменные
  model.ts                общие контракты: PlayerSnapshot, TrackInfo, Activity, Config
  log.ts                  логгер с уровнями в stderr (под systemd попадает в journald)
  sources/
    mpris.ts              D-Bus: находит плеер по Identity "YandexMusic", подписки, опрос позиции
    mprisTracker.ts       чистая логика без D-Bus: сырые свойства MPRIS → PlayerSnapshot | null
  enrich/
    index.ts              CachingEnricher: цепочка провайдеров, LRU-кэш, single-flight, backoff
    yandex.ts             поиск api.music.yandex.net/search → id трека/альбома/артистов, обложка 400x400
    itunes.ts             iTunes Search → только обложка 600x600 (запасной вариант)
    matcher.ts            строгое сопоставление кандидата со снимком плеера
    http.ts               общий GET JSON: таймаут, User-Agent, классификация ошибок
  presence/
    build.ts              чистая функция: снимок + TrackInfo + конфиг → Activity
    engine.ts             КОГДА отправлять: debounce, ожидание обложки, AFK, dedupe, throttle
    consoleSink.ts        dry run: печатает activity вместо отправки
  discord/
    ipc.ts                собственный клиент локального RPC Discord: кадры, handshake, переподключение
    socketPaths.ts        где искать discord-ipc-N (нативный, Flatpak, Snap, Vesktop)
scripts/
  dump.ts                 пробный запуск с живым плеером, всегда без Discord
  live-mpris.ts           только снимки MPRIS, по одной JSON-строке
  install-service.sh      установка systemd --user юнита из packaging/
```

Зависимость времени выполнения одна: `@jellybrick/dbus-next` (поддерживаемый форк `dbus-next`, чистый JS). Протокол Discord IPC реализован вручную в `discord/ipc.ts`.

## Поток данных

```
MPRIS (D-Bus)                                    Discord IPC (unix-сокет)
   │ PropertiesChanged, Seeked, Get/GetAll            ▲ SET_ACTIVITY
   ▼                                                  │
MprisSource ─► MprisTracker ─► PlayerSnapshot ─► App ─► PresenceEngine ─► DiscordIpc
                                                  │          ▲
                                                  │ trackKey │ setTrackInfo(trackKey, info)
                                                  ▼          │
                                           CachingEnricher ──┘
                                           (Yandex → iTunes)
```

1. `MprisSource` находит плеер, подписывается на сигналы и отдаёт сырые свойства в `MprisTracker`.
2. `MprisTracker` сглаживает причуды MPRIS (см. ниже) и выдаёт `PlayerSnapshot`: статус, название, артисты, альбом, длительность, позиция на момент `at`, оценка скорости и `trackKey`. `null` означает, что плеер пропал.
3. `App` передаёт каждый снимок в `PresenceEngine`. Если `trackKey` новый, `App` запускает поиск в каталоге, а предыдущий незавершённый поиск отменяет через `AbortSignal`.
4. Результат поиска (`TrackInfo` или `null`) уходит в `engine.setTrackInfo()`. Ответ для устаревшего трека игнорируется.
5. `PresenceEngine` решает, когда и что отправлять, и вызывает `buildActivity()`.
6. `DiscordIpc` держит одно долгоживущее соединение и отправляет `SET_ACTIVITY`. После переподключения он сам повторяет последнюю activity.

## Снимок плеера (`PlayerSnapshot`)

- `trackKey` строится по содержимому: `${title}|${artists}|${round(durationMs / 1000)}`. Повтор того же трека даёт тот же ключ: перезапуск приходит как перемотка.
- `status: 'stopped'` окончательный: трекер выдаёт его только после двухсекундного grace, название при этом может быть пустым. Получатели просто очищают карточку.
- `rate` никогда не приходит из MPRIS, а оценивается по Δpos/Δt.

## Причуды MPRIS

Яндекс Музыка — Electron-приложение, MPRIS за неё публикует Chromium (имя `org.mpris.MediaPlayer2.chromium.instance<PID>`, Identity `YandexMusic`). Особенности, которые учитывает `mprisTracker.ts`:

- **Поля приходят по одному.** При смене трека отдельные `PropertiesChanged` несут сначала новый `mpris:trackid`, потом длину, название, артиста и альбом. Трекер ждёт 250 мс тишины (но не дольше 1 с от начала пачки), затем перечитывает все свойства через `GetAll` и только после этого решает.
- **Мигание `Stopped`/`NoTrack`.** Между треками плеер на десятки миллисекунд уходит в `Stopped` с `mpris:trackid = /org/mpris/MediaPlayer2/TrackList/NoTrack` и пустыми полями. Такое состояние сообщается, только если продержалось 2 с.
- **`mpris:trackid` не идентифицирует трек.** Это id медиа-сессии Chromium (`/org/chromium/MediaPlayer2/TrackList/Track<hex>`): соседние треки несут один и тот же id, меняется он только на мигании `NoTrack`. Поэтому `trackKey` строится по содержимому.
- **Артисты одной строкой.** `xesam:artist` содержит один элемент `"A, B"`; трекер делит его по `", "`. `[""]` означает «нет артистов».
- **`Rate` всегда 1.** Скорость воспроизведения через MPRIS не сообщается. Пока играет музыка, источник раз в 5 с читает `Position`. Если за интервал не короче 2 с позиция стабильно идёт со стандартной скоростью (0.5, 0.75, 1, 1.25, 1.5, 1.75, 2; допуск 0.08) два опроса подряд, трекер принимает новую скорость. Пока скорость подтверждается, расхождение не считается перемоткой.
- **Перемотка.** `Seeked` приходит не всегда, поэтому расхождение опрошенной позиции с ожидаемой больше чем на 1,5 с тоже считается перемоткой. После `Seeked` источник перечитывает `Position`.
- **Потоки без длительности** (генеративные подборки) могут держать `Position` на месте. Если длины нет, неподвижная позиция не считается перемоткой, и счётчик продолжает идти от первого снимка.
- **Обложка в MPRIS бесполезна:** `mpris:artUrl` указывает на временный локальный файл, а Discord принимает только https-картинки. Поэтому нужен поиск по каталогу.
- **Чужие плееры.** Браузеры публикуют свои MPRIS-объекты на том же пути `/org/mpris/MediaPlayer2`. Источник сверяет отправителя каждого сигнала с unique name плеера Яндекс Музыки (вида `:1.42`) и подписывается только на него.
- **Только чтение.** Источник вызывает лишь `Properties.Get/GetAll` и подписывается на сигналы. Методы `Player` (Play, Pause, Next и т. д.) не вызываются никогда.
- **Жизненный цикл.** Появление и исчезновение плеера ловится через `NameOwnerChanged`, плюс страховочный пересмотр списка имён раз в 10 с. Если пропала сама сессионная шина, карточка сразу очищается, а источник переподключается каждые 10 с.

## Поиск в каталоге

- **Яндекс:** `GET https://api.music.yandex.net/search?text=<артисты и название>&type=track&page=0&nocorrect=true`, без токена. Даёт id трека, альбома и артистов, `version` и `coverUri`; обложка получается заменой `%%` на `400x400`. Принимаются только картинки с `avatars.yandex.net` (или `avatars.mds.yandex.net`).
- **iTunes:** `GET https://itunes.apple.com/search?term=…&entity=song&limit=10`. Только обложка (`artworkUrl100` → 600x600); ссылки всегда ведут в Яндекс, поэтому iTunes не даёт ни id, ни ссылок.
- **Порядок.** Сначала Яндекс. Если он не нашёл обложку или недоступен, iTunes дополняет только обложку.
- **Матчер** (`matcher.ts`). Неверная обложка или ссылка хуже, чем никакой, поэтому кандидат отбрасывается, если:
  - название не совпадает после нормализации (NFKC, нижний регистр, ё→е, без диакритики, без `feat.`), допускается только «название + version» каталога;
  - хотя бы один артист из плеера не найден у кандидата;
  - у кандидата есть пометка «karaoke», «instrumental», «cover» и подобные, которой нет у плеера;
  - длительность отличается больше чем на max(8 с, 4%).

  Оставшиеся получают баллы: точное название, близость длительности, совпадение альбома, наличие обложки, доступность трека. Порог 80, при равенстве выигрывает оригинал без `version` и более ранний результат поиска.
- **Кэш** (`CachingEnricher`): LRU на 128 записей. Найденное живёт 6 ч, «не найдено» — 30 мин; частичный ответ (какой-то провайдер пропущен) — 30 мин и только если что-то найдено; ошибки не кэшируются. Одинаковые одновременные запросы объединяются (single-flight); запрос отменяется, когда его больше никто не ждёт.
- **Backoff провайдера:** 10 мин после HTTP 451/403/429/5xx, 60 с после сетевой ошибки или таймаута (5 с), либо `Retry-After` в пределах 60 с – 1 ч. Если трек не нашёлся, `App` повторяет поиск один раз через 60 с (настоящий промах к тому времени лежит в кэше и ничего не стоит).

## Activity

`presence/build.ts` строит activity типа Listening (`type: 2`). Пример для «PinkPantheress — Capable of love» (данные каталога из `test/fixtures/yandex-search-capable-of-love.json`; позиция 70 742 мс из 223 747 мс в момент `now = 1793450000000`):

```json
{
  "type": 2,
  "name": "Яндекс Музыка",
  "status_display_type": 1,
  "details": "Capable of love",
  "details_url": "https://music.yandex.ru/album/28127004/track/118138322",
  "state": "PinkPantheress",
  "state_url": "https://music.yandex.ru/artist/12044483",
  "timestamps": { "start": 1793449929258, "end": 1793450153005 },
  "assets": {
    "large_image": "https://avatars.yandex.net/get-music-content/9837405/0f61442d.a.28127004-1/400x400",
    "large_text": "Heaven knows",
    "large_url": "https://music.yandex.ru/album/28127004"
  },
  "buttons": [
    { "label": "Слушать в Яндекс Музыке", "url": "https://music.yandex.ru/album/28127004/track/118138322" }
  ],
  "instance": false
}
```

Правила:
- `details` — название (с `version` из каталога в скобках, если она есть), `state` — артисты через запятую. Ссылки на трек и артиста ставятся, только если трек найден в Яндексе.
- `large_text` — альбом, если он отличается от названия трека (у синглов совпадает, тогда поле не ставится).
- `large_image` — обложка, без неё ключ `assets.logo` из конфига.
- **Пауза:** `timestamps` нет (замороженной полосы в Discord не бывает), `small_image` = `assets.paused`, `small_text` = «На паузе».
- **Без длительности:** только `start`, Discord показывает счётчик «прошло» вместо полосы.
- **Остановлено или плеер пропал:** activity `null`, карточка очищается.
- Пустые поля не отправляются вовсе; кнопка без ссылки не добавляется.

### Полоса прогресса

`start = at − positionMs / rate`, `end = start + durationMs / rate`, в epoch-миллисекундах. Полосу рисует и двигает клиент каждого зрителя по своим часам, поэтому каждую секунду ничего отправлять не нужно. При `rate ≠ 1` доля заполнения верна, а показанная длительность масштабируется. Значения проверяются через `Number.isFinite`: одно `NaN` отклонило бы всю команду.

## Когда отправлять (`presence/engine.ts`)

| Событие | Действие |
|---|---|
| Новый `trackKey` | Отложенная карточка прошлого трека отбрасывается. Ждём 400 мс, пока доедут поля, затем ждём результат поиска до 1,5 с от смены трека, чтобы не отправлять «логотип, потом обложку» двумя обновлениями. Не дождались — уходит карточка с логотипом, обложка следом. |
| Пауза | Карточка без полосы со значком паузы; запускается AFK-таймер на `afkMinutes`. |
| Продолжение | Новые timestamps, AFK-таймер сбрасывается. |
| AFK истёк | Очистка. При следующем Playing карточка вернётся. |
| Перемотка, смена скорости | Пересчёт timestamps; отправка, только если `start` или `end` сдвинулись больше чем на 2 с. |
| `stopped`, плеер пропал | Очистка сразу (grace уже выдержан источником). |
| Discord отклонил обложку (`ERROR`) | URL запоминается как плохой, карточка сразу переотправляется с логотипом вне очереди throttle. |
| SIGINT/SIGTERM | Очистка, закрытие сокета, выход (не дольше 5 с). |

- **Dedupe.** Ключ — activity без timestamps с отсортированными полями; если он совпадает с последним отправленным, а timestamps сдвинулись не больше чем на 2 с, ничего не шлём.
- **Throttle.** Leading + trailing, не чаще раза в 4 с; уходит всегда самое свежее состояние. Отправки идут строго по одной, поэтому старый результат не может перекрыть новый.
- **Часы.** Интервалы (debounce, throttle, TTL, backoff) считаются по монотонным часам (`performance.now()`), `Date.now()` идёт только в timestamps. Иначе шаг системного времени назад заморозил бы обновления.

## Discord IPC

- **Сокет:** `discord-ipc-0` … `discord-ipc-9` в `$XDG_RUNTIME_DIR`, `$TMPDIR`, `$TMP`, `$TEMP`, `/run/user/$UID`, `/tmp` и подкаталогах Flatpak/Snap/Vesktop (`socketPaths.ts`). Пробуются только пути, где действительно лежит сокет.
- **Кадр:** int32LE opcode + int32LE длина + UTF-8 JSON. Opcodes: 0 HANDSHAKE, 1 FRAME, 2 CLOSE, 3 PING, 4 PONG.
- **Сессия:** HANDSHAKE `{"v": 1, "client_id": "<Application ID>"}` → `DISPATCH READY` → команды `{"cmd": "SET_ACTIVITY", "args": {"pid": …, "activity": {…}}, "nonce": "<uuid>"}`. Ответ сопоставляется по `nonce`; `evt: "ERROR"` превращается в `DiscordRpcError`. `args` без `activity` очищает карточку.
- **Переподключение:** паузы 5, 10, 20, 30 с (дальше по 30 с). После `READY` повторяется последняя желаемая activity. Отклонённая activity не становится целью повтора: желаемым остаётся то, что Discord принял последним.
- **Неверный client id:** Discord закрывает соединение с кодом 4000; демон пишет об этом в лог и пробует раз в 30 с.

### Лимиты Discord

Это факты о поведении десктопного клиента, на которые опирается код:

- Строки `details`, `state`, `large_text`: 2–128 символов (короче дополняются невидимым символом U+2800, длиннее обрезаются с «…»); `name`: 1–128.
- `details_url`, `state_url`, `large_url`: URI не длиннее 256; `large_image`: ключ ассета или https-URL до 300 символов. Слишком длинные ссылки не обрезаются, а выбрасываются: обрезанный URI не прошёл бы проверку.
- Кнопок 1–2 (пустой массив не отправляется), `label` до 32 символов, `url` до 512. Свои кнопки пользователь не видит.
- Timestamps: целые миллисекунды epoch, ≥ 1.
- Одно невалидное поле отклоняет всю команду. Если Discord не может загрузить внешнюю картинку, он тоже отклоняет всю команду (`ERROR`, обычно код 1000).
- Обновления presence: не больше 5 за 20 с на весь presence пользователя (все приложения вместе); лишние клиент откладывает. Отсюда throttle в 4 с.
- Handshake ограничен для каждого client id (несколько подряд, дальше примерно раз в 30 с), поэтому демон держит одно долгоживущее соединение.
- Activity типа Listening всегда уступает запущенной игре.

## Почему не так, как другие

**Мод `app.asar`, как у PulseSync.** PulseSync подменяет `app.asar` Яндекс Музыки своей сборкой и читает плеер изнутри приложения. Так доступны точные данные (id, обложка, версия трека), но для этого нужны права на каталог установки (root или pkexec), пакетный менеджер перезаписывает мод при каждом обновлении, правки в минифицированных чанках приходится переносить на каждую новую сборку, а распространяется изменённый код Яндекса. Этот проект ничего в приложении не меняет.

**CDP (`--remote-debugging-port`).** Если запустить Яндекс Музыку с отладочным портом, можно читать состояние плеера из страницы без изменения файлов и получить те же точные данные. Но приложение придётся перезапускать через свой ярлык с флагом, а открытый порт даёт любому локальному процессу возможность выполнять JavaScript в залогиненном приложении: прочитать токен, управлять воспроизведением. К тому же скрипт зависит от внутренностей страницы, которые меняются от сборки к сборке. Возможно, когда-нибудь появится как опция по явному согласию.

**Ynison.** Это протокол синхронизации воспроизведения Яндекса (WebSocket); через него видно даже то, что играет на телефоне. Но он требует OAuth-токен с полным доступом к аккаунту, который получают через client id официального приложения (серая зона условий использования). Десктопный клиент нередко публикует там неточное состояние (например, «пауза» во время игры), в состоянии нет артистов, а сервис иногда сбоит. MPRIS + поиск по каталогу обходятся без токена.

## Тесты

`node --test 'test/**/*.test.ts'`. Трекер проверяется на детерминированных часах, в том числе на записанной и обезличенной смене трека (`test/fixtures/mpris-track-change.jsonl`, формат `busctl monitor --json`). `MprisSource` — на отдельном `dbus-daemon` во временном сокете с фейковыми плеерами, `DiscordIpc` — на фейковом сервере Discord во временном unix-сокете. Ни настоящая сессионная шина, ни настоящий Discord в тестах не используются.
